# Консоль: ролі та доступ

Консоль використовує наявні `AdminUser`, Bearer JWT і `MnpPerson`.
Окрема модель клієнта або окрема база не створюється.

| Можливість | Суперадмін | Адмін | Менеджер |
| --- | --- | --- | --- |
| Створювати клієнта | Так | Так | Так |
| Переглядати й редагувати клієнтів | Усіх | Усіх | Власних і призначених |
| Надавати менеджеру доступ до клієнта | Так | Так | Ні |
| Керувати працівниками | Усі ролі | Менеджери | Ні |
| Переглядати публічні сторінки сайту | Так | Ні | Ні |
| Каталог професій у консолі | Так | Так | Ні |

Сторінки сайту тимчасово закриті перевіркою сесії у frontend.
Без входу будь-який frontend-маршрут показує лише форму авторизації.
Відкриті API каталогу та ринкової статистики залишаються відкритими:
це не механізм приховування загальнодоступних даних від HTTP-клієнтів.
Приватні API Person KB перевіряють роль та доступ до конкретного профілю
на сервері, включно з усіма вкладеними операціями.

Таблиця `mnp_person_access` зберігає автора та додаткові дозволи.
Автор залишається автором; відкликати можна додатковий дозвіл.
Історичні автори відновлюються з подій `person_created` журналу аудиту.
Якщо автора неможливо встановити, клієнт доступний адміністраторам;
вони можуть надати доступ менеджерам вручну.
Вимкнення облікового запису діє одразу, навіть для вже виданого токена.
Роль читається з БД на кожному запиті, а не з переданої клієнтом ролі.

## Локальний запуск

Запустіть `dev.py` через **Run Python File in Terminal** або F5.
При першому запуску введіть свій email і пароль у терміналі.
Буде створено особистого суперадміна і вимкнено відомий тестовий вхід
`admin@mnp.local`. Пароль прихований під час введення й зберігається як bcrypt-хеш.
Підписувальний ключ генерується локально в gitignored `data/dev/.console-jwt-key`.

Повторне локальне налаштування власника: `python -m scripts.console_setup`.
Ця команда працює тільки з локальною SQLite-базою розробки.
`Ctrl+C` у терміналі `dev.py` зупиняє backend і frontend.

## Розгортання

Перед запуском оновленого backend застосуйте **нову** міграцію
`alembic upgrade head` до потрібної бази. Старі міграції не змінено.
Обов’язково налаштуйте приватний `JWT_SECRET` у середовищі сервера.
Обліковий запис власника у production потрібно налаштувати окремо
в цільовій базі через наявний механізм провізіонування; локальний
скрипт навмисно не змінює production. Публікація змін не виконувалась.

Перевірки: `tests/test_workspace_access.py` покриває ізоляцію менеджерів,
перегляд/зміну чужого UUID, вкладені факти, надання й відкликання доступу,
підвищення привілеїв, вимкнення облікового запису та зміну ролі з чинним токеном.
